# Software Requirements Specification (SRS)
## AI Hallucination Mitigation System (v2.0.0)

---

## 1. Introduction

### 1.1 Purpose
This Software Requirements Specification (SRS) document specifies the functional, non-functional, interface, and performance requirements for the **AI Hallucination Mitigation System**. It serves as the formal specification baseline for developers, researchers, evaluators, and system architects.

### 1.2 Scope
The software system provides an automated pipeline for detecting, evaluating, explaining, and mitigating factual hallucinations in natural language text generated by Large Language Models or provided by users. The system encompasses:
- Web-based user interface for real-time verification and exploratory analysis.
- RESTful backend API offering modular endpoints for verification, answer generation, document indexing, and user history.
- AI/ML verification ensemble combining Natural Language Inference, semantic similarity, token-level probability heuristics, and contradiction detection.
- Hybrid multi-source evidence retriever accessing external knowledge bases and local document corpora.
- Visual explanation generator rendering dynamic Knowledge Graphs and confidence breakdowns.

### 1.3 Definitions & Glossary
- **Hallucination:** Content generated by an LLM that is nonsensical, factually incorrect, or unfaithful to the provided source context.
- **Intrinsic Hallucination:** Generated information that directly contradicts the source or reference evidence.
- **Extrinsic Hallucination:** Generated information that cannot be verified or substantiated from the source context.
- **Entailment:** A directional relationship between two text segments where the truth of the hypothesis follows necessarily from the premise.
- **Contradiction:** A relationship where the hypothesis cannot be true given the truth of the premise.
- **Neutral / Unverified:** A relationship where the premise does not provide sufficient evidence to confirm or deny the hypothesis.
- **Atomic Claim:** A single, self-contained factual proposition isolated from complex sentences.

### 1.4 Acronyms
- **API:** Application Programming Interface
- **BM25:** Best Matching 25 (Probabilistic Information Retrieval Algorithm)
- **CORS:** Cross-Origin Resource Sharing
- **CRUD:** Create, Read, Update, Delete
- **FAISS:** Facebook AI Similarity Search
- **F1:** Harmonic Mean of Precision and Recall
- **HMR:** Hot Module Replacement

## 2. Overall Description

### 2.1 Product Perspective
The system operates as an autonomous, self-contained platform with client-server architecture:
- **Client Tier:** React 19 Single-Page Application (SPA) with TanStack Router running in modern web browsers.
- **Server Tier:** FastAPI asynchronous server providing modular microservices.
- **AI/ML Engine Tier:** PyTorch & Transformers pipelines running on CPU/GPU hardware.
- **Data Tier:** Dual-mode persistence layer with MongoDB Atlas primary connection and local in-memory fallback store.
- **External Integration Tier:** Wikipedia REST API, Semantic Scholar API, and arXiv API.

│                 Client Layer (Browser)                      │

                               │ HTTPS / JSON

│                FastAPI Application Server                   │

### 2.2 Product Functions
1. **Direct Claim Verification:** Validates user-submitted factual claims against user-provided or auto-retrieved evidence.
2. **Answer Verification & Grounding:** Audits complete LLM answers by breaking them into atomic claims, retrieving multi-source evidence, and scoring hallucination risk.
3. **Evidence-Grounded Question Answering (RAG):** Answers user questions strictly grounded in retrieved evidence with inline citations.
4. **Document Corpus Management:** Enables users to upload, chunk, embed, and query custom files (PDF, TXT, MD, CSV, DOCX).
5. **Dynamic Knowledge Graph Rendering:** Visualizes entities, relations, and source attributions in an interactive graph canvas.
6. **Evaluation & Benchmarking:** Evaluates hallucination mitigation accuracy on TruthfulQA, HaluEval, and FEVER benchmark datasets.

### 2.3 User Characteristics & Personas
- **General User:** Requires a simple input box, intuitive verdict badges ("Supported", "Refuted", "Uncertain"), clear citations, and easy sharing.
- **AI Researcher / Academic:** Requires granular confidence scores, access to individual verification method outputs (NLI vs. token probability vs. semantic cosine similarity), and benchmark execution tools.
- **System Administrator / Developer:** Requires OpenAPI/Swagger documentation, Dockerized/modular execution, health endpoints, and database mode indicators.

### 2.4 Constraints
- **Hardware Resources:** System designed to execute on consumer hardware (x86_64, Windows/Linux/macOS, minimum 8GB RAM) with CPU inference capability.
- **Python Runtime:** Python 3.10+ required due to modern type hint features.
- **Node.js Runtime:** Node.js 18+ required for Vite 8 frontend bundling.
- **External Network Dependency:** Online mode requires connectivity to Wikipedia and Hugging Face Hub; offline fallback operates on cached models and local documents.

### 2.5 Assumptions & Dependencies
- Input text is in the English language.
- Hugging Face model weights (`cross-encoder/nli-deberta-v3-small`, `sentence-transformers/all-MiniLM-L6-v2`) are cached locally after initial execution.
- If MongoDB connection URI is absent, system smoothly continues operation in in-memory storage mode without data corruption.

## 3. Functional Requirements

### FR-01: Claim Verification Endpoint
- **Description:** System shall verify a user claim against provided evidence or auto-retrieved evidence using the multi-method ensemble.
- **Input:** JSON payload `{ "claim": string, "evidence"?: string, "methods"?: string[] }`.
- **Processing:** 
  1. Validate payload via Pydantic model.
  2. If evidence is empty, trigger Multi-Source Retriever (Wikipedia, arXiv, Semantic Scholar).
  3. Execute selected verification algorithms (Cross-Encoder, Token Probability, Semantic Similarity).
  4. Compute weighted ensemble confidence and determine verdict (`SUPPORTED`, `REFUTED`, `UNCERTAIN`).
  5. Extract entity triples and generate Knowledge Graph structure.
- **Output:** JSON object containing `claim`, `verdict`, `confidence`, `is_hallucinated`, `methods_used`, `evidence_sources`, `entities`, and `knowledge_graph`.
- **Preconditions:** FastAPI backend is running.
- **Postconditions:** Verification record is persisted to database/memory history.

### FR-02: LLM Answer Fact-Checking
- **Description:** System shall audit a generated answer against retrieved facts and compute hallucination risk.
- **Input:** JSON payload `{ "query"?: string, "answer": string, "documents"?: string[] }`.
- **Processing:**
  1. Decompose multi-sentence answer into atomic propositions using regex/NLP boundaries.
  2. Retrieve reference documents for each proposition if not provided.
  3. Run NLI stance evaluation for each claim.
  4. Aggregate overall hallucination risk score ($0.0 \dots 1.0$), source reliability score, and contradiction flag.
- **Output:** JSON object containing overall `verification_status`, `confidence_score`, `hallucination_risk_score`, array of `claims` with individual verdicts, and array of `sources`.
- **Preconditions:** Backend engine active.
- **Postconditions:** Answer verification record stored in history.

### FR-03: RAG Grounded Question Answering
- **Description:** System shall answer a user question using evidence-grounded generation and abstain if evidence is insufficient.
- **Input:** JSON payload `{ "query": string, "max_sources"?: int, "enable_grounding"?: bool }`.
- **Processing:**
  1. Perform hybrid retrieval (BM25 + Dense vector search) across external and local indices.
  2. Rerank top-$K$ chunks using cross-encoder scoring.
  3. Construct grounded prompt with explicit citation requirements.
  4. Synthesize answer and perform post-generation verification.
  5. If confidence is below threshold ($\tau = 0.35$), trigger abstention message.
- **Output:** JSON object containing `query`, `answer`, `verification_status`, `confidence_score`, `sources`, and `citations`.
- **Preconditions:** Query text is non-empty.
- **Postconditions:** Citations match retrieved source chunks.

### FR-04: Document Upload & Indexing
- **Description:** System shall accept document file uploads (PDF, TXT, MD, DOCX, CSV), extract text, split into chunks, and index into vector and keyword stores.
- **Input:** Multipart form upload (`file`, `title`?).
- **Processing:**
  1. Validate file extension and size ($\le 20\text{MB}$).
  2. Parse text content using PyPDF2 or UTF-8 text decoder.
  3. Chunk text into 500-token windows with 50-token sliding overlap.
  4. Generate embeddings via `all-MiniLM-L6-v2`.
  5. Index chunks into in-memory/FAISS vector store and BM25 index.
- **Output:** JSON object `{ "document_id": string, "filename": string, "chunks_count": int, "status": "indexed" }`.
- **Preconditions:** Uploaded file is valid format.
- **Postconditions:** Document chunks are searchable via `/api/documents/search`.

### FR-05: Dynamic Knowledge Graph Extraction
- **Description:** System shall extract named entities and relational predicates from verified claims and evidence.
- **Input:** Claim and evidence text.
- **Processing:**
  1. Apply noun-phrase and dependency pattern extraction.
  2. Link subject-predicate-object triples.
  3. Calculate co-occurrence edges across evidence chunks.
  4. Format into graph nodes (id, label, type) and edges (source, target, label).
- **Output:** JSON object `{ "nodes": [...], "edges": [...] }`.
- **Preconditions:** Valid text input.
- **Postconditions:** Formatted for `@xyflow/react` frontend rendering.

### FR-06: Verification History & Data Management
- **Description:** System shall provide full CRUD operations over verification history.
- **Input:** GET/POST/DELETE requests to `/api/history`, `/api/history/{id}`, `/api/history/clear`.
- **Processing:**
  1. Retrieve paginated records from database or in-memory cache.
  2. Filter by status (`supported`, `refuted`, `uncertain`).
  3. Delete specific records or wipe collection upon user confirmation.
- **Output:** Paginated list of verification logs or operation success status.
- **Preconditions:** User requested valid history resource.
- **Postconditions:** Database state is updated consistently.

### FR-07: Benchmark Evaluation Runner
- **Description:** System shall execute automated benchmark evaluations on TruthfulQA, HaluEval, and FEVER subsets.
- **Input:** Benchmark configuration parameters (dataset name, sample size, threshold).
- **Processing:**
  1. Load benchmark questions and labeled claims.
  2. Execute verification pipeline across all test items.
  3. Calculate Precision, Recall, F1, Accuracy, Hallucination Rate, and Latency.
- **Output:** JSON summary report with metric tables and confusion matrix data.
- **Preconditions:** Benchmark datasets present in `data/benchmarks/`.
- **Postconditions:** Results saved to `data/results/` for analysis.

## 4. Non-Functional Requirements (NFRs)

### NFR-01: Performance & Latency
- Single claim verification latency shall not exceed **1.5 seconds** on consumer 4-core CPU hardware.
- Pre-cached embedding generation shall execute in **$\le 50\text{ms}$** per chunk.
- Frontend initial page load (FCP) shall be under **1.2 seconds** on standard broadband.

### NFR-02: Reliability & Fault Tolerance
- System shall maintain **99.9% uptime** in local deployment mode.
- If MongoDB connection drops or is unconfigured, the backend shall seamlessly switch to in-memory fallback without throwing unhandled exceptions (HTTP 500).
- If an external retrieval API (e.g., Semantic Scholar) returns HTTP 429/500, the system shall fall back to Wikipedia and local documents without failing the user request.

### NFR-03: Scalability
- The FastAPI async backend architecture shall support at least **50 concurrent requests** in local single-worker mode and scale linearly with Uvicorn worker processes.
- The document retrieval engine shall support indexing up to **10,000 text chunks** in memory with sub-100ms cosine similarity search.

### NFR-04: Security & Privacy
- Zero hardcoded API keys or plaintext database passwords shall exist in source code repository.
- File upload handlers shall enforce strict MIME type validation and path traversal sanitization.
- CORS policy shall restrict origin access to authorized client domains.
- No user-submitted claim or document text shall be transmitted to third-party tracking services.

### NFR-05: Maintainability & Code Quality
- Backend code shall conform to PEP 8 standards with full type annotations.
- Frontend code shall adhere to ESLint 9 and Prettier formatting rules with zero TypeScript `tsc --noEmit` errors.
- Unit and integration test suite shall maintain $>80\%$ code coverage across verification modules.

### NFR-06: Usability & Accessibility
- The UI shall adhere to WCAG 2.1 AA accessibility guidelines, including keyboard navigation, ARIA attributes, and high-contrast color badges.
- Visual feedback (loading spinners, progress bars, toast notifications) shall accompany all asynchronous API operations.

### NFR-07: Availability
- The system services (backend and frontend) shall support background daemon execution with continuous health check monitoring via `/api/health`.
